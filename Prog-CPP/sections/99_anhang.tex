\subsection{Styleguide}

\begin{itemize}[itemsep=1pt, parsep=0pt]
    \item \textbf{Variablen, Konstanten}
    \begin{itemize}[itemsep=1pt, parsep=0pt]
        \item mit Kleinbuchstaben beginnen
        \item erster Buchstaben von zusammengesetzten Wörtern ist gross (mixed case)
        \item keine Underscores
    \end{itemize}
    Beispiele : counter, maxSpeed
    \item \textbf{Funktionen}
    \begin{itemize}[itemsep=1pt, parsep=0pt]
        \item mit Kleinbuchstaben beginnen
        \item erster Buchstaben von zusammengesetzten Wörtern ist gross (mixed case)
 
        \item Namen beschreiben Tätigkeiten
        \item keine Underscores
    \end{itemize}
    Beispiele : getCount(), init(), setMaxSpeed()
    \item \textbf{Klassen, Strukturen, Enums}
    \begin{itemize}[itemsep=1pt, parsep=0pt]
        \item mit Grossbuchstaben beginnen
        \item erster Buchstaben von zusammengesetzten Wörtern ist gross (mixed case)
        \item keine Underscores
        \item Namen beschreiben Dinge
    \end{itemize}
   
    Beispiele : MotorController, Queue, Color
\end{itemize}

\subsection{Rückgabe per Referenz und Method Chaining}
\begin{itemize}
    \item \textbf{Mechanismus:} Eine Funktion sendet exakt hier eine Referenz auf das Objekt selbst per \texttt{return *this;} zurück. Der Return-Typ muss zwingend Referenz sein (z.B. \texttt{Complex\&}).
    \item \textbf{Kaskadierung (Cascading):} Macht es möglich, sehr viele Methoden am Stück auf der gleichen Instanz pro Zeile zu rufen: \texttt{obj.funz1().funz2();}.
    \crd{Mit einem Return \textit{by-value} würde jene funz2 auf \textit{tmp} Objekt angewendet}
    \item \textbf{Effizienz:} Im Gegensatz zu dem Return by Value entsteht gar keine Kopie der Daten (absolut kein \textit{tmp} Hilfsobjekt), was massiv Ressourcen schont.
    \item \textbf{Persistenz:} Alle Änderungen tief in dieser Kette wirken nun wirklich ganz direkt auf das Original-Objekt statt auf eine zur Löschung verurteilte Kopie.
\end{itemize}

\subsection{Non-Type Template Parameter (Static Allocation)}

Diese Templates akzeptieren konstante Werte (Bsp. \texttt{std::size\_t N}), die erst via \textbf{Compile-Time} evaluiert werden. 
Dies ist der einzige Weg, die Array-Grösse statisch festzulegen (\texttt{T data[N]}), um die hohe Flexibilität des Code zu wahren.
In C++ muss der Compiler den exakten Platzbedarf vom Objekt drüben im \textbf{Stack} kennen, um Maschinen-Instruktionen mit recht fixen \textit{Offsets} zu gen.
Wäre das \texttt{N} Variablen-basiert, so wüsste der Compiler echt überhaupt nicht, wie viel Platz zu reservieren ist, und die Allokation fiele durch.
\subsubsection{Statische Allokation vs Dynamik}
Ohne Auflösung bei der Compile-Time kann der Compiler keinen Platz exakt drüben im \textbf{Stack} blockieren, was zur Nutzung vom \textbf{Heap}-Memory zwingt (das ist träger).
\resizebox{\columnwidth}{!}{
\begin{tabular}{|l|l|l|}
\hline
\textbf{Eigenschaft} & \textbf{Via Template (statisch)} & \textbf{Via Konstruktor (dynamisch)} \\ \hline
\textbf{Grössenlimit}   & Konstante am Compiletime & Variabel am Run-Time \\ \hline
\textbf{Memory}        & Stack (schnell, fix)   & Heap (flexibel und träge) \\ \hline
\textbf{Verwaltung}       & Automatisch (0 Memory Leaks) & Manuell (\texttt{new}/\texttt{delete}) \\ \hline
\textbf{Typ-Effekt}   & \texttt{Class<10>} $\neq$ \texttt{Class<20>} & Der Typ bleibt identisch \\ \hline
\end{tabular}}

\subsection{Inline Functions und Templates}

\begin{itemize}
    \item \textbf{Implizites Inlining:} Alle Funktionen (ob Template o. nicht), die komplett innerhalb der Deklaration in einer Klasse (\textit{in-class}) stehen, gelten als völlig automatisch \texttt{inline} durch den C++ Compiler.
    \item \textbf{Explizites Inlining:} Template-Fkt., die exakt ausserhalb der Klasse (\textit{out-of-class}) stehen (auch wenn im selben Header platziert), sind absolut \textbf{nicht} ganz per Default einfach so \texttt{inline}. 
    Um dies wirklich zu erzwingen, muss das \texttt{inline}-Keyword zwischen dem \texttt{template}-Tag und dem eigentlichen Return-Typ ganz fest drin stehen.
    \item \textbf{Vorteile und Limits:} Das Inlining tilgt exakt den Overhead des Fkt.-Aufrufs (\textit{Zero Overhead}), ist jedoch sehr stark abgeraten für komplex-rekursive Funktionen.
\end{itemize}
